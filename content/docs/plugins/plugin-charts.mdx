## Usage

The plugin provides two chart APIs:

1. **Simple Bar Chart** (`bar-chart`) - Simplified API for basic bar charts
2. **Advanced Charts** (`chart`) - Full-featured API supporting multiple chart types (bar, line, area) and multiple data series

### Basic Usage

```tsx
// Import once in your app entry point
import '@object-ui/plugin-charts'
import type { BarChartSchema } from '@object-ui/plugin-charts'

// Use in schemas
const schema: BarChartSchema = {
  type: 'bar-chart',
  data: [
    { name: 'Jan', value: 400 },
    { name: 'Feb', value: 300 },
    { name: 'Mar', value: 600 }
  ],
  dataKey: 'value',
  xAxisKey: 'name',
  height: 400
}
```

## Features

- **Bar, line, and area charts**
- **Responsive design**
- **Customizable colors and styles**
- **Lazy-loaded** (~540 KB loads only when rendered)

## Schema API

```plaintext
{
  type: 'bar-chart',
  data?: Array<Record<string, any>>,  // Chart data
  dataKey?: string,                    // Y-axis data key
  xAxisKey?: string,                   // X-axis label key
  height?: number,                     // Chart height
  color?: string,                      // Bar color
  className?: string                   // Tailwind classes
}
```

### BarChartSchema

Declared by `@object-ui/plugin-charts` (`packages/plugin-charts/src/types.ts`).
It extends `BaseSchema`, so the shared component properties are available on a
`bar-chart` node as well as the ones below.

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `data` | Array of objects | `[]` | Array of data objects to visualize |
| `dataKey` | string | `'value'` | Key in data objects for Y-axis values |
| `xAxisKey` | string | `'name'` | Key in data objects for X-axis labels |
| `height` | number | `400` | Chart height in pixels |
| `color` | string | `'#8884d8'` | Primary color for bars/lines |
| `className` | string | `''` | Additional Tailwind CSS classes |

## Chart Types

The plugin provides two different chart components:

### Simple Bar Chart (bar-chart)

For basic single-series bar charts, use the simplified `bar-chart` type:

```tsx
import type { BarChartSchema } from '@object-ui/plugin-charts'

const schema: BarChartSchema = {
  type: 'bar-chart',
  data: [
    { month: 'Jan', sales: 400 },
    { month: 'Feb', sales: 300 },
    { month: 'Mar', sales: 600 }
  ],
  dataKey: 'sales',
  xAxisKey: 'month',
  color: '#3b82f6',
  height: 300
}
```

### Advanced Charts (chart)

For multi-series charts or line/area charts, use the advanced `chart` type with the `chartType` property:

##### Bar Chart

```tsx
import type { ChartSchema } from '@object-ui/types'

const schema: ChartSchema = {
  type: 'chart',
  chartType: 'bar',
  data: [
    { month: 'Jan', sales: 400, target: 350 },
    { month: 'Feb', sales: 300, target: 400 },
    { month: 'Mar', sales: 600, target: 550 }
  ],
  xAxisKey: 'month',
  series: [
    { dataKey: 'sales' },
    { dataKey: 'target' }
  ],
  config: {
    sales: { label: 'Sales', color: '#3b82f6' },
    target: { label: 'Target', color: '#10b981' }
  }
}
```

##### Line Chart

```tsx
import type { ChartSchema } from '@object-ui/types'

const schema: ChartSchema = {
  type: 'chart',
  chartType: 'line',
  data: [
    { date: '2024-01', users: 120 },
    { date: '2024-02', users: 180 },
    { date: '2024-03', users: 250 }
  ],
  xAxisKey: 'date',
  series: [
    { dataKey: 'users' }
  ],
  config: {
    users: { label: 'Users', color: '#8884d8' }
  }
}
```

###### Area Chart

```tsx
import type { ChartSchema } from '@object-ui/types'

const schema: ChartSchema = {
  type: 'chart',
  chartType: 'area',
  data: [
    { time: '9:00', value: 20 },
    { time: '10:00', value: 35 },
    { time: '11:00', value: 45 }
  ],
  xAxisKey: 'time',
  series: [
    { dataKey: 'value' }
  ],
  config: {
    value: { label: 'Value', color: '#10b981' }
  }
}
```

##### Per-series options

Each `series` entry names the column it plots (`dataKey`, or the spec spelling `name`) and may carry the presentation keys the renderer reads — the same keys as `@objectstack/spec`'s `ChartSeries`:

| Key | Type | Effect |
|---|---|---|
| `label` | `string` or inline locale map | Legend / tooltip name; defaults to the column key. |
| `type` | `'bar' \| 'line' \| 'area'` | Per-series family override — a combo chart is a series disagreeing with the chart's `chartType`. |
| `color` | `string` | Series colour; wins over the positional palette. |
| `stack` | `string` | Stack group id — series sharing one id stack together. |
| `yAxis` | `'left' \| 'right'` | Which y-axis the series binds to, on a chart that declares a second y-axis. |
| `variant` | `'primary' \| 'comparison'` | `comparison` draws the muted period-over-period overlay; `primary` (the default) is the normal treatment. The muted defaults are per mark family; a `radar` overlay takes the `area` ones, radar being the other mark this renderer both strokes and fills. |
| `dashArray` | `string` | SVG `stroke-dasharray`, e.g. `"4 4"` for a dashed line. Applies on **any** series, whatever its `variant`, and overrides the comparison overlay's default `"4 4"`. Only a mark with a stroke can show a dash, and this renderer strokes `line`, `area` and `radar` marks (the chart's `chartType`, or a per-series `type` override) — on a `bar` or `scatter` mark the value reaches the mark and paints nothing, which is the mark's geometry rather than a condition on the key. |
| `opacity` | `number` | Stroke and fill opacity override — any finite number (the spec bounds it to 0–1). Applies on **any** series, whatever its `variant`, on every mark family — the fill of a `bar` or `scatter` mark, the stroke of a `line` mark, both on an `area` or `radar` mark — and overrides the comparison overlay's per-family default. |

`chartType` is **not** a series key. It is the renderer's internal spelling of `type` — `@objectstack/spec`'s `ChartSeries` lists it as an alias — and the validator refuses it by name (`Unrecognized key(s) on this chart series: chartType. Did you mean chartType → type?`) instead of dropping it silently, which is what it used to do. Write `type`.

An `area` chart keeps every key in this example live: `stack` stacks the two primary areas, and the comparison overlay takes both the dash and the opacity (on a `bar` chart the dash would still reach the mark, but a bar has no stroke to dash). Neither key needs `variant: 'comparison'` — a primary series may carry them too, and then it is the overlay's defaults, not the keys, that stay comparison-only.

```tsx
import type { ChartSchema } from '@object-ui/types'

const schema: ChartSchema = {
  type: 'chart',
  chartType: 'area',
  data: [
    { month: 'Jan', revenue: 400, cost: 250, revenue_prev: 360 },
    { month: 'Feb', revenue: 300, cost: 210, revenue_prev: 330 }
  ],
  xAxisKey: 'month',
  series: [
    { name: 'revenue', label: 'Revenue', stack: 'money' },
    { name: 'cost', label: 'Cost', stack: 'money' },
    // '8 4' overrides the overlay's default '4 4' dash; 0.6 lifts its 0.2 fill default (its stroke default is already 0.6)
    { name: 'revenue_prev', label: 'Revenue (previous period)', variant: 'comparison', dashArray: '8 4', opacity: 0.6 }
  ]
}
```

##### Axis options

`xAxis` and `yAxis` take `@objectstack/spec`'s axis object — the `ChartAxis` a dashboard widget's `chartConfig` uses, with the same keys and the same checks. `xAxis` is one object; `yAxis` is a **list**, one entry per value axis, and a second entry declares the right-hand axis. The object is strict: an undeclared key is refused at parse, with the spec's own hint (`Did you mean grid → showGridLines?`).

| Key | Type | Effect |
|---|---|---|
| `field` | `string` | **Required.** The column the axis reads. On `xAxis` it names the category column (`xAxisKey` wins when both are written); on `yAxis`, when the chart has neither `series` nor `categories`, the entries' `field`s are the plotted columns. |
| `title` | `string` or inline locale map | Axis title, resolved to the viewer's language. |
| `format` | `string` | Tick number format, e.g. `"$0,0.00"` or `"0.0%"`. A string the renderer does not recognise keeps the default ticks. |
| `min` / `max` | `number` | Pin the ends of a numeric axis: the value axes, and the x axis of a `scatter` chart. |
| `stepSize` | `number` | Distance between ticks on a numeric axis. |
| `showGridLines` | `boolean` | `false` on the first `yAxis` entry hides the horizontal grid lines; `true` on `xAxis` draws vertical ones. |
| `position` | `'left' \| 'right' \| 'top' \| 'bottom'` | The side of the chart the axis belongs to. On `xAxis` it is one of the two sides that axis can run along: `top` or `bottom` on bar, line, area and `scatter` charts, whose x axis runs across the plot; `left` or `right` on a `horizontal-bar` chart, where `xAxis` configures the category axis running down the plot. Any other side draws the axis at its default side (the bottom; the left on `horizontal-bar`), and the chart shows a note under the plot naming `xAxis.position`. |
| `logarithmic` | `boolean` | Logarithmic scale on a numeric axis. |

A bare string is not an axis object. `xAxis: 'month'` is the sibling spelling of `xAxisKey` and folds onto it at parse; a single object or a bare string on `yAxis` is refused — write a one-entry list.

```tsx
import type { ChartSchema } from '@object-ui/types'

const schema: ChartSchema = {
  type: 'chart',
  chartType: 'line',
  data: [
    { month: 'Jan', revenue: 4000, margin: 0.21 },
    { month: 'Feb', revenue: 3000, margin: 0.18 }
  ],
  xAxis: { field: 'month', title: 'Month' },
  yAxis: [
    { field: 'revenue', title: 'Revenue', format: '$0,0', min: 0 },
    // the second entry is the right-hand axis the `margin` series binds to
    { field: 'margin', title: { en: 'Margin', fr: 'Marge' }, format: '0.0%' }
  ],
  series: [
    { name: 'revenue' },
    { name: 'margin', yAxis: 'right' }
  ]
}
```

## Bundle Size

The plugin uses lazy loading to optimize bundle size:

- **Initial load**: ~0.2 KB (entry point)
- **Lazy chunk**: ~541 KB minified (~136 KB gzipped)
- **Loads only when rendered**

Without lazy loading, this would add 541 KB to your main bundle. With lazy loading, it's loaded only when charts are displayed.

## Axis Tick Labels and the Host Page Font

**Precondition:** the host page's `body` font family must match the font family the chart's axis tick labels render with. When the two differ, Recharts computes its tick-density and collision decisions against the wrong glyph metrics: tick labels overlap when the page font is narrower than the tick font, and labels that would have fitted are dropped from the axis when it is wider. Nothing reports the mismatch — there is no error and no warning, only a different set of visible labels.

To meet it, render charts in the page's body font: set your font stack on `body`, and do not give a chart, or any element between `body` and the chart, a different `font-family`.

Why it happens: on any axis whose `interval` is not a number — Recharts' default `preserveEnd`, and `preserveStart`, `preserveStartEnd`, `equidistantPreserveStart` and `equidistantPreserveEnd` — Recharts chooses which tick labels to keep by measuring every label: its width on a horizontal axis, its height on a vertical one. It takes that measurement in a hidden `span` that it appends to `document.body`, so the span inherits the page's body font family rather than the chart's. After the first render Recharts reads the computed `fontSize` and `letterSpacing` back from a rendered tick and measures again with them, but it never reads `fontFamily`, and a `fontFamily` in an axis's `tick` props does not reach the measurement either. A numeric `interval` (such as `0`) skips the measurement altogether. The fix belongs in Recharts itself; it is tracked in [objectui#9430](https://github.com/objectstack-ai/objectui/issues/9430).

This package has one instance of it. `ChartImpl`, the component the `bar-chart` type lazy-loads, sets `fontFamily: 'monospace'` in its y-axis `tick` props and gives that axis no `interval`, so the axis runs Recharts' default `preserveEnd` thinning and its labels are measured in the page's body font instead of in monospace. Its x-axis carries the same font but sets `interval={0}`, which skips the measurement. Because a vertical axis measures label heights, and the measuring `span` is one line tall — its height comes from the `line-height` it inherits from `body`, and depends on the font family only when that `line-height` is `normal` — this y-axis can keep a different set of labels only on a page that leaves `line-height` at `normal`.
