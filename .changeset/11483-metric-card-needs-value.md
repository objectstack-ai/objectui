A `metric-card` in a dashboard's widget slot parses only with its `value` (objectui#11483). This narrows a published accept set on both validator faces, and it narrows the widget `type` vocabulary the TypeScript face exports. `minor`, per this repository's version alignment; the narrowing is the breaking part.

`DashboardWidgetTypeSchema` is the widget arm's `type` vocabulary. It named the component type `metric-card`, taken from `DASHBOARD_COMPONENT_WIDGET_TYPES`. So `{ type: 'metric-card', title: 'Revenue' }` in `widgets[]` parsed as a widget, because it carries only keys both arms accept. It parsed on `AnyComponentSchema` / `DashboardComponentSchema` and on `StrictAnyComponentSchema`. The card's required `value` (objectui#11467) governed only a card that also carried `icon`, `trend` or `trendValue`. The dashboard then drew the card with an empty figure.

- **What changed.** `DashboardWidgetTypeSchema` is now the spec's families plus `list` and `custom`, so the slot reads a `metric-card` through its component arm alone. The TypeScript twin, `DashboardWidgetTypeName`, drops `DashboardComponentWidgetType` the same way. `DASHBOARD_COMPONENT_WIDGET_TYPES` still lists `metric-card`: it is the component arm's `type`, and only that.
- **What now refuses that did not.** Directly in `widgets[]`, both faces refuse a `metric-card` with no `value`. That holds whatever else the card carries: `title`, `description`, `id` and `layout`, a `dataset` with `values`, or its figure under `options` (`options: { value }`), which the tolerant face accepted. On its own, `DashboardWidgetSchema` (zod) refuses `type: 'metric-card'` at `type`. On the TypeScript face, `'metric-card'` is no longer a `DashboardWidgetTypeName`, so assigning it to that type is a compile error.
- **Why no widget key stands in for `value`.** This was measured through the real `DashboardRenderer` and `DashboardGridLayout`. A `dataset` makes the dashboard draw `DatasetWidget` in the card's place, by a rule that does not read the `type`; the card is never mounted. `options` is spread onto the node as literal props: a second spelling of `value`, not a binding. No other widget key reached the figure.
- **What does not move.** On the TypeScript face, `DashboardWidgetSchema['type']` still includes `'metric-card'`. That interface is also the read type of every `widgets[]` entry, and the component arm stays assignable to it. So a `metric-card` literal with no `value` still compiles directly in `widgets[]`, while the validator refuses it on both faces. A `metric-card` in a widget's legacy `component` envelope is judged as before: there, the tolerant face's `BaseSchema` fallback still accepts a card that fails the arm. Every `metric-card` in the schema catalog, the READMEs and the docs fences carries its `value`. The one docs example that did not, under "TypeScript Support" in `content/docs/plugins/plugin-dashboard.mdx`, is rewritten.

**Fix:** give the card its `value`. For a figure queried from a dataset, write a `metric` widget (`{ type: 'metric', dataset, values: [measure] }`), which the dashboard draws as the same dataset tile.

⚠️ **Dated note, 2026-10-03 — the TypeScript widget arm drops the component type too — objectui#11514.** At this change, "What does not move" above held: `DashboardWidgetSchema['type']` still included `'metric-card'`, the interface was the read type of every `widgets[]` entry, the component arm was assignable to it, and a `metric-card` literal with no `value` still compiled directly in `widgets[]`. Now `DashboardWidgetSchema['type']` is `DashboardWidgetTypeName` alone, `plugin-dashboard`, `plugin-designer` and `app-shell` read an entry by the slot's element type (`DashboardComponentSchema['widgets'][number]`), the component arm is no longer assignable to the widget arm, and `tsc` refuses a `metric-card` with no `value` as both validator faces do. `.changeset/11514-types-widget-arm-type.md` states what ships. The rest of this entry is kept as the reading of this change.
